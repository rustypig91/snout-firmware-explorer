A standalone Rust desktop application and CLI for understanding embedded firmware memory usage. The first milestone targets **ARM Cortex-M and GCC**, with generic ELF models that leave room for other architectures.

## Opening firmware and selecting supporting files

Install a current stable Rust toolchain. Windows builds need the Visual Studio C++ Build Tools and Windows SDK. Linux desktop builds need a working X11 or Wayland session and development packages for Wayland, xkbcommon and OpenGL (on Ubuntu: `libwayland-dev libxkbcommon-dev libgl1-mesa-dev`). The CLI and core do not require desktop libraries.

```sh
cargo build --workspace --locked
cargo run -p firmware-gui -- fixtures/build --elf cortex-m.elf
```

Pass `--elf FILE` to select firmware automatically after the folder scan. Relative file paths are resolved inside the supplied build folder. You can also open an ELF directly: `firmware-gui fixtures/build/cortex-m.elf`. With no path, Snout opens the last build folder and restores the saved workspace. Opening the same build folder without an explicit ELF selection restores the last selected firmware if it is still present. An explicit ELF selection takes priority; a missing saved ELF leaves the folder open for selection.

**Settings** is anchored at the bottom-left of the sidebar and contains folder, configuration, update, analysis-note, support and About actions. Select **Open build folder**, press Ctrl+O, or drag a folder into the window. **Settings > Open recent build folder** remembers the five most recently opened folders across restarts. Reopening a folder moves it to the top without adding a duplicate. The application recursively scans for linked ELF images (including `.elf`, `.axf`, `.out` and extensionless images), linker maps (`.map`) and stack reports (`.su`). The header’s ELF dropdown lists firmware images using paths relative to the build folder. Select an image to analyze it; selection is disabled during background loads. **Build files**, directly below **Overview** in the left sidebar, opens a dedicated tab with map radio buttons and a separate stack-report directory tree for the current ELF. Map filenames open previews, which retain actions for memory-region and cross-reference imports. **Back to file selection** returns from a preview, and **Back to Overview** returns to the dashboard. Folders without firmware still allow supporting-file previews. Failed selections retain the last successful firmware report. Select **Settings > Refresh** or press F5 after rebuilding. Settings shortcut hints also show **Ctrl+O** to open a build folder and **F1** for About.

Selecting firmware automatically imports memory-region capacities from a unique matching GNU ld or Texas Instruments CGT map (`app.map` or `app.elf.map` for `app.elf`), preferring a sibling file. Ambiguous or unsupported maps leave capacity unknown and produce analysis notes. Map matching is filename-based, not proof that artifacts came from the same build. Use a map’s radio button in **Build files** to select its memory regions. Manual map choices are remembered for each firmware image in each build folder across restarts. Chosen maps are read again when reopening or refreshing firmware after a rebuild. The map currently supplying memory regions has its radio button selected in **Build files**. **Settings > Reset settings for this build folder** clears that folder’s saved choices and rediscovers the current firmware’s matching map. Linker scripts are not listed or evaluated. Memory roles are inferred from map region names and attributes. See the [GNU linker documentation](https://sourceware.org/binutils/docs/ld/Options.html) for generating a link map.

Map previews automatically identify GNU ld, Texas Instruments CGT, and LLVM lld ELF formats from their contents. TI CGT import supports old `attributes` tables and newer `used / unused / attr` tables, hexadecimal values, and non-overlapping `PAGE` groups. Capacities come from region lengths; usage remains calculated from the ELF. Explicit FLASH/ROM names take precedence over TI's often-permissive `RWIX` attributes. Empty TI ranges are skipped. Overlapping page address spaces and recognized word-addressed C28x/C54x/C55x targets are rejected because the current memory model requires one byte-addressed physical space. TI cross references and section/object attribution are not imported. Unknown formats are identified as unsupported. See [TI's linker-map example](https://software-dl.ti.com/codegen/docs/tiarmclang/rel3_1_0_STS/compiler_manual/linker_description/12_linker_example/linker-example-stdz0759199.html).

LLVM lld ELF maps (`VMA LMA Size Align Out In Symbol`) support a parsed **LLVM output section placement** preview with runtime/load addresses and sizes, plus dependency import from `--cref` tables. Generate these with `-Wl,-Map,app.map,--cref,--no-demangle` when linking with lld. Automatic matching and manual **Use cross references from this map** both work. LLVM maps do not report physical region capacities: physical capacities remain unknown. The section preview does not alter ELF analysis. LLVM's COFF, Mach-O, and WebAssembly map dialects are not supported. See [LLVM's ELF map writer](https://github.com/llvm/llvm-project/blob/main/lld/ELF/MapFile.cpp).

ELF/DWARF information always takes precedence over map information for symbol and source attribution. Maps supplement the ELF with region capacities and supported linker cross references; they never overwrite DWARF ownership or symbol sizes/addresses.

When firmware is selected, Snout guesses `.su` reports from linker-map object paths, matching target directories, or unambiguous ELF function matches. Review or change the selection with file and recursive directory checkboxes under **Stack usage files (.su)** in the **Build files** tab. Choices are saved per ELF immediately and restored on refresh and restart, including an empty selection. Selected directories include future reports; selecting a file includes future siblings while preserving existing unchecked files. Reports can span several targets or configurations, so verify their build ownership. The Stack view defaults to entries with candidates in the selected ELF and preserves report paths and matching evidence. Gray bars behind Local frame byte counts compare each row with the largest visible frame: a full cell is 100%, and half the bytes fills half the cell. Enable **Show unresolved reports** to inspect entries that could not be associated. Functions without matching reports are counted with unknown local stack size. No call-chain totals are invented.

The dark navy interface uses green accents, a firmware dropdown and left navigation. Navigation buttons highlight on hover; the selected view has a green edge. The Settings row reserves separate space for its gear and label, with the full row opening the menu. The left navigation includes Overview, Build files, Baselines, Files, Symbols, Sections, Memory regions, Dependencies, Stack, and Hex viewer. **Build files** is a normal sidebar tab directly below **Overview**. Interface text has a 12 pt minimum; labels inside the zoomable dependency diagram scale with zoom.

Overview fits six bordered cards into the available screen without a scrollbar: Binary information, Memory usage, Flash and RAM Section type distributions, Top functions by size, and Top files by size. Binary information, Memory usage and both distributions occupy the upper row; two wider rankings occupy the lower row. Card titles wrap in narrower windows. The upper row reserves enough height to keep both memory-region controls and the regions link visible at the minimum 900 × 600 window size. Rankings show up to ten entries, adapting the visible count to available height; links open the full tables. Functions include only ELF Function symbols, ranked by unique Flash contribution. Files exclude unattributed storage and are also ranked by unique Flash contribution. Row tooltips retain complete names, addresses and byte counts; clicking a row opens its symbols. Binary information aligns labels and values in two columns. Each section-distribution donut uses smooth circular edges and a palette assigned in descending size order, independent of section names, with distinct colors for all visible slices and a matching, aligned name/percentage legend. The donuts show current Flash payload and static RAM usage respectively, with Flash and RAM center labels, grouping sections after the largest five as Other. Their legends open the Sections table. Snapshot filtering does not change the donuts, while rankings retain the Overview difference filter and size annotations. Memory usage keeps full Flash payload and static RAM totals in the block tooltips, separately from physical occupancy. Each block starts directly with a region dropdown and a green Flash or blue RAM occupancy bar, with percentage inside the bar and used/capacity and free bytes below. The dropdown shows only the region name. It defaults to the region of that kind with the highest occupancy percentage (ties keep layout order); an explicit selection stays by name while that region remains available. Selections are saved immediately per ELF path within its build folder and restored on refresh, firmware switches and restarts. If a saved name no longer exists for that memory kind, the highest-occupancy region is shown instead; if no regions of that kind exist, capacity is unknown. Preferences without saved selections use the default without a migration. Unknown capacity is labeled explicitly without a bar. View all regions opens Memory regions. Tooltips retain complete byte counts and explain runtime uncertainty. The header ELF selector shows a file icon, filename, firmware path, and chevron in a two-line button; its popup lists available firmware. Beside it, the header shows ELF format, the analyzed architecture, and bit width. This information wraps onto a second header row in narrower windows.

Analysis notes remain available from **Settings > Analysis notes**; detailed sizes and attribution remain in the Files, Symbols, Sections and Memory regions views.

Tables support search and sorting, with right-aligned numeric columns. Columns fit their content when space allows and share spare width in smaller windows. Widths update when the window or table data changes; manual resizing remains available. Gray bars in the Size/ELF size, Flash and RAM columns of Sections, Symbols and Files compare each value with its own column’s largest visible value. Click a row to expand its details directly underneath; click it again to collapse. Expanded file rows include a button to inspect their symbols. Enable Directories for an optional source tree sidebar. Baseline cards highlight on hover and mark the selected comparison; **None** in the Baselines tab clears it; a header badge shows the current selection and clears it when clicked. The badge is hidden when no baseline is selected. Escape collapses the expanded row and notes. Firmware stays local. The CLI continues to accept individual ELF paths.


The **Dependencies** tab shows a hierarchical compilation-unit graph with clickable boxes and curved arrows, pan/zoom, directory grouping, search, and a focused neighborhood view. It flows top-to-bottom in tall canvases and left-to-right in wide canvases. Box area scales linearly from 0 B at a minimum size measured from the labels to the largest visible Flash/RAM contribution at 25 times that minimum area. Labels grow with their boxes, and each box displays its byte count. Large graphs wrap broad dependency ranks into compact bands, with nearby connections routed through shared gutters. Filtering shows matching units and their directly connected dependencies and dependents, within the selected-unit focus when enabled. Switching memory modes or filtering recalculates and fits the layout. Arrows run from a unit using a symbol to the unit defining it; selecting an arrow lists the connecting symbols. Sizes count attributed symbol bytes, excluding padding and unknown ownership. DWARF compilation-unit ownership takes priority over ELF unit labels; source locations in headers do not create units.

To supply connections, generate a GNU ld or LLVM lld ELF linker map with `-Wl,-Map,app.map,--cref,--no-demangle`. A unique matching map loads automatically with firmware. Alternatively, select a map in **Build files** and choose **Use cross references from this map**. Explicit dependency-map choices are saved per firmware independently of memory layouts and reread on F5 and restart. Failed explicit imports preserve the current report; an unavailable saved map leaves source nodes visible with a note and no stale connections.

Cross references include functions, global data, and function addresses, and may include discarded code; they do not prove runtime calls. Source-unit connections require a global ELF definition of the connecting symbol; symbols missing from the ELF are omitted because they may be unresolved or discarded. Object-only graphs cannot distinguish unresolved weak references from definitions in GNU ld cross-reference tables, so their arrows need verification. Object/archive paths associate with source units only through exact ELF symbol definitions with one consistent unit owner. Ambiguous or unknown objects remain separate nodes with unknown memory contribution. LTO and stripped builds can limit source association. Without cross references, the graph shows known units and explains that connections are unavailable; an isolated node is not proof of independence. The committed Cortex-M fixtures include six source units and sixteen connections, including reciprocal dependencies; open `fixtures/build/cortex-m.elf` from the build folder to explore them. Weak aliases can inherit ownership from an exact function range with one known unit; conflicting owners remain ambiguous. ELF-only CLI JSON includes unit nodes in the additive `dependencies` field; automatic map import applies to build-folder analysis.


```sh
cargo run -p firmware-cli -- analyze fixtures/build/cortex-m.elf
cargo run -p firmware-cli -- files fixtures/build/cortex-m.elf
cargo run -p firmware-cli -- symbols fixtures/build/cortex-m.elf
cargo run -p firmware-cli -- diff fixtures/build/cortex-m.elf fixtures/build/cortex-m-grown.elf
cargo run -p firmware-cli -- stack fixtures/build/cortex-m.elf --stack-usage fixtures/build/CMakeFiles/cortex-m-objects.dir/src
cargo run -p firmware-cli -- analyze fixtures/build/cortex-m.elf --format json
cargo run -p firmware-cli -- analyze fixtures/build/cortex-m.elf --map fixtures/build/cortex-m.map --format json
```

CLI `analyze`, `files`, `symbols`, and `stack` accept `--map FILE`. Maps supply physical memory regions (GNU ld/TI CGT) and dependency cross references (GNU ld/LLVM lld with `--cref`). JSON reports retain the imported map path, source/object evidence, connecting symbols, and limitations. LLVM maps provide no physical capacities; these remain unknown. JSON memory-layout files and `--config` are no longer supported.

The CLI uses ELF inference when `--map` is omitted and never automatically chooses a map. Pass maps explicitly for comparisons using `diff OLD.elf NEW.elf --old-map OLD.map --new-map NEW.map`. Verify that each map belongs to its ELF. Missing/unreadable maps, unsupported formats, malformed memory regions, or malformed cross-reference tables exit with status 1 and a diagnostic on stderr. Valid maps without cross references still report memory usage and explain how to generate `--cref` connections. Argument errors (including removed `--config`) exit with status 2. Desktop automatic matching requires a unique same-name map, preferring a unique sibling; ambiguous matches never select an arbitrary map.

For optimized standalone executables:

```sh
cargo build --workspace --release --locked
```

Executables are `target/release/firmware-gui` and `target/release/firmware-explorer` (with `.exe` on Windows). Neither requires a Rust installation on the destination machine. Desktop platform libraries still apply.

## Releases and updates

The [build workflow](../.github/workflows/build.yml) follows Pigtail's Windows/Linux release workflow. Run it manually on a branch, or label a PR `build`, `build-linux`, or `build-windows` to produce downloadable artifacts. Pushing `v<workspace-version>` publishes a GitHub release; the workflow rejects tags that do not match `Cargo.toml`.

Release assets include portable archives containing the GUI and CLI, standalone GUI executables for the updater, Windows MSI and Setup installers, a Debian package, and an AppImage. Linux builds also capture `snout-screenshot.png` using the regular app with `fixtures/build/cortex-m.elf` selected. There is no demo build. The screenshot runs in an isolated Xvfb session with fresh preferences and update checks disabled.

Build packages locally using `bash scripts/build-release.sh` on x86_64 Debian/Ubuntu or `scripts\build-release.cmd` from a Windows developer shell. Output goes to `target/release-assets/<target>/`. The Linux script needs the desktop build packages listed above, plus `curl`, `pkg-config`, and `dpkg-dev`; packaging downloads linuxdeploy and installs cargo-deb if needed. Windows requires Rust, the C++ Build Tools and Windows SDK; the script downloads portable WiX and Inno Setup. To capture a screenshot locally, install `xvfb xauth xdotool imagemagick`, then run:

```sh
bash scripts/capture-screenshot.sh target/release/firmware-gui target/snout-screenshot.png fixtures/build/cortex-m.elf
```

Snout checks GitHub releases at startup. **Settings → Check for updates** provides a manual check. **Support developer** opens Buy Me a Coffee, and **About** shows the app version and repository link. Startup checks stay quiet on network errors, when up to date, or for a skipped version. Download and installation begin only when you press **Update**, and the download's published size and SHA-256 digest are verified before installation. Workspace preferences are saved before installing and restored after restarting. Portable binaries update in place, AppImages replace the original AppImage, and Windows Setup installations reuse their existing installation scope. Debian installations use the package manager instead. MSI installations are identified by this product’s Windows Installer UpgradeCode and the registered executable component, and offer a **Download MSI installer** button instead of in-app replacement. Run that MSI to upgrade the registered installation. Portable copies remain eligible for self-updates even when an MSI is installed elsewhere. If Windows Installer ownership cannot be checked, in-app replacement is disabled and the downloads page remains available. `--no-update-check` suppresses the startup request for one launch.

## Architecture

```text
firmware-gui (egui/eframe) ─┐
                          ├── firmware-analysis-core
firmware-cli (clap) ───────┘       ├── ELF adapter: goblin
                                  ├── DWARF: gimli + addr2line
                                  ├── accounting / attribution / tree
                                  ├── comparison
                                  └── compiler stack reports / call-graph model
```

The core accepts a path or byte slice plus analysis options and returns a serializable `Analysis`. Parser types stay internal. Frontends do not perform accounting. GUI analysis runs on a worker thread, and failed loads preserve the last successful report. Memory configuration changes are validated and applied together with a successful reanalysis.

The CLI's `analyze`, `files` and `symbols` JSON modes return the same complete report envelope, including `schema_version`, options, warnings, sections, symbols, file totals and address ranges. `diff` and `stack` have their own versioned envelopes. Comparison reports include section, file and symbol deltas; same-name sections are aggregated. Sizes and addresses are exact integers; signed comparison deltas are bytes. Exit status is zero for successful analysis (including documented missing information), nonzero for invalid input or command usage. No CI policy engine is included yet.

Use **Baselines** in the left sidebar to save, overwrite, or delete named firmware snapshots. Click a saved baseline card in the Baselines tab to select it; click the selected card again or select **None** to clear comparison. **Delete all baselines** removes the snapshots listed for the current firmware after confirmation. Each baseline card shows a large name on the left, smaller muted capture date/time and ELF path beside it, and a bin icon on the right. Capture times use the computer’s local timezone. The bin icon opens deletion confirmation without changing the selected comparison. The sidebar tab lists saved names, ELF paths and capture times. Saving shows a progress screen; overwriting or deleting opens a centered confirmation that blocks the background. Completing or canceling these operations returns to the Baselines tab. Saving does not automatically select the new baseline. The default tabs display changed sizes as `170.00 KiB (+1.00 KiB)` and changed addresses as `0x20000400 (+0x400)`. Unchanged values keep their normal display; new entries are marked `(new)`. Percentages show differences in percentage points. Snapshots are saved as individual JSON files under `snout-firmware-explorer/snapshots/<build-folder-id>/<firmware-id>/<snapshot-id>.json` in the user configuration directory. Saved snapshots survive refreshes and restarts. Baseline selection lasts only for the current session; the app starts with no baseline selected. At startup, snapshot folders are removed when their build folder is no longer listed in the saved build settings, and empty snapshot directories are pruned. Deleting a snapshot also removes any empty firmware, build, and snapshot storage directories. Folder and file names use compact stable IDs so identical names from different builds remain separate and paths stay short on Windows. Display names are stored in the JSON files. Nothing is saved to the build folder. Selecting **None** in the Baselines tab returns to the usual display without deleting snapshots. Resetting build-folder settings preserves snapshots. Selecting a baseline automatically shows only added, removed, and changed entries in every tab. The header identifies the active baseline; clicking its badge clears comparison without changing tabs. The badge is hidden when no baseline is selected. Creation and deletion are available only from the Baselines tab. The table toolbar retains **Show address changes** while comparing. Overview applies the filter to its rankings; firmware totals remain the full current totals.

Source files use consistent short paths across the desktop views, keeping at least the parent directory and filename and adding parents to distinguish duplicates across the whole report. Hover shows the full absolute source path; relative compiler paths use a unique matching DWARF source or the build folder when available. ELF compilation-unit labels without a proven file location remain labels. Full paths remain searchable in file tables. The directory tree keeps its folder hierarchy and shows full source paths on hover. The desktop overview shows static RAM composition and an expandable explanation of unattributed bytes by section. BSS and reservation categories use section naming conventions; no-load storage alone does not establish how startup initializes it. Stack summaries show the largest uniquely matched local frame and explain why total stack is unknown. Reports without ELF matches remain visible when no matches exist, including stripped firmware. A loaded comparison highlights the largest Flash/RAM increases and links to the Sections, Files and Symbols comparison tables. F5 keeps the baseline snapshot while reloading current firmware and rereading selected map/JSON layouts. You can drop a build folder or an ELF into the window.

### Parsing and UI choices

- [goblin](https://docs.rs/goblin/0.10.7/goblin/elf/struct.Elf.html) exposes ELF section and program headers, including physical load addresses, directly. This avoids writing a production binary parser.
- [gimli and addr2line](https://docs.rs/addr2line/0.25.1/addr2line/) provide DWARF line lookup. `cpp_demangle` and `rustc-demangle` preserve raw symbol names alongside readable names.
- [egui/eframe](https://docs.rs/eframe/0.30.0/eframe/) provides a native Rust desktop frontend with virtualized table rows, contextual help and no web frontend build step. Versions are pinned by `Cargo.lock`; deliberate dependency upgrades should run the full checks.
- [layout-rs](https://docs.rs/layout-rs/0.1.3/layout/) arranges dependency boxes and routes curves in-process, with cached geometry drawn interactively in egui. No Graphviz installation is required. Disassembly dependencies remain deferred until there is a concrete call-graph implementation to validate.

## What the numbers mean

**Flash payload** is the sum of allocated, file-backed section bytes inferred to be stored in Flash. Non-allocated debug data, ELF headers, segment padding, gaps between addresses and programmer-specific image overhead are excluded. `metadata.segment_file_bytes` separately reports the sum of `PT_LOAD` file sizes; do not add it to Flash usage.

**RAM at runtime (static)** counts sections inferred to occupy RAM, including explicit heap/stack reservations represented as allocated sections. It is **not** a prediction of all memory needed during execution. Runtime allocation, unreserved stacks, interrupt overhead and OS allocations remain unknown.

| Storage | Flash payload | Static RAM |
|---|---:|---:|
| Read-only code and constants | yes | normally no |
| Initialized writable data | yes | yes |
| Code copied to RAM, identified by different load/run addresses | yes | yes |
| Allocated `SHT_NOBITS` storage such as BSS or stack reservations | no | normally yes |
| Debug information | no | no |

Classification uses allocation/write flags, section type, and matching `PT_LOAD` mappings, **not section-name lists**. For file-backed sections, the load address is `p_paddr + (sh_offset - p_offset)` after checking both file and virtual containment and their relative offsets. ARM function addresses are normalized for the Thumb bit during attribution; the raw value is retained. `SHT_NOBITS` means no file payload; it does not prove how startup initializes that memory.

Hex viewer displays a continuously scrolling, 16-byte-per-line hexdump of the current firmware. Only visible lines are decoded and formatted; scrolling uses a bounded virtual window so large sparse address ranges stay responsive without losing individual address precision. Choose Flash load contents or RAM startup contents, optionally narrowed to a configured memory region. Byte, halfword, word and doubleword grouping and little/big endian controls default to the ELF bitness and byte order. ASCII remains in address order. Enter a hexadecimal address or exact symbol/section name to jump to its highlighted line; section and symbol starts appear at the right with byte offsets and hover details. Hover a name to outline its exact byte extent in both hex and ASCII, including across lines and within endian-formatted values. Hover an individual hex byte to outline that byte and its corresponding ASCII character and see its exact address, value and content provenance, plus every section and symbol covering it with their start addresses, sizes and byte offsets. Byte tooltips follow the selected endian order within grouped values and include zero-sized labels only at their exact address. Padding before or after the selected range has no byte tooltip or byte hover outline. Zero-sized labels have no inferred extent. RAM combines file-backed initial values (including code copied to RAM) with blue, inferred zeros for conventional `.bss`, `.sbss` and `.dynbss` sections. Startup code is not verified. Reservations, gaps, segment padding and unavailable bytes appear as `??`; erased Flash, runtime relocations, heap, stack and live RAM are not inferred. Without configured regions, bounds cover the ELF section ranges, not the full chip capacity. Hex viewer always displays current firmware and does not compare against a baseline. Raw memory bytes remain session-only and are excluded from JSON reports and snapshots.

ELF metadata does not conclusively identify physical memory technology. Writable, copied, and no-payload allocated sections are inferred as RAM under the bare-metal model. Memory regions imported from linker maps classify matching load/runtime ranges. A region must contain the entire range. Uncovered ranges produce warnings and retain inferred classification. In Memory regions, each configured region shows its address bounds, capacity, used/free bytes and percentage used. Each region has a green Flash or blue RAM occupancy bar in a scrollable list; search filters region names. Symbols are inspected in the Symbols tab. Without configured regions, this tab shows inferred load/runtime address ranges instead. Import regions through Memory regions > Load memory regions by selecting a `.map` file. Occupancy counts the union of allocated load and runtime section ranges intersecting each physical region, including padding and reservations, without counting the same addresses twice. Boundary-crossing sections count only their intersection; analysis notes still flag incomplete coverage. Free space means capacity minus static ELF occupancy, not guaranteed runtime headroom or a contiguous allocation. Without map-provided regions, capacity and free space remain unknown. Stripped files retain section usage but may have no symbols.

### Attribution and uncertainty

- Function source paths and lines come from DWARF address lookup, refined by definitions matching the symbol name and address. Supported variable definitions also supply source ownership. This is symbol-level attribution, not byte-by-byte ownership of inlined code.
- Local symbols can fall back to ELF `STT_FILE` compilation-unit labels. These are **not proven object-file paths**. Global symbols are not assigned to whichever file label happened to precede them.
- File totals include an explicit **unattributed** bucket for unknown owners, padding, reservations and uncovered bytes. File/tree totals reconcile with the overview.
- Symbol sizes remain the ELF values. Zero-sized labels do not acquire guessed sizes. Overlapping symbols/weak aliases share unique memory contributions, assigned once in section/address/name order. File attribution can consequently depend on which alias owns shared bytes.
- Stack entries retain compiler qualifiers (`static`, `dynamic`, `dynamic,bounded`) and ELF candidates matched by exact symbol name, DWARF source file/line, or a demangled function name without parameters. Known conflicting source paths are excluded; source locations disambiguate overloads when available. Zero matches are unresolved; multiple matches are ambiguous. Reports must belong to the same build. No call targets or call-chain stack totals are invented.

## Current boundaries and next milestones

This is the first implementation milestone, not a claim of universal firmware support.

1. **Attribution:** extend DWARF definition support and add GNU linker MAP object/archive ownership. Map import reads region capacities and GNU ld / LLVM lld symbol cross references for the dependency graph; section/object memory accounting is not yet imported. Variable attribution supports direct address expressions; location lists, TLS, complex expressions and definitions requiring reference resolution remain unsupported. Global variables without a matching supported definition remain unattributed. Compressed and split/external DWARF are not supported.
2. **Memory layouts:** add saved target profiles, explicit unknown memory roles, overlay policies and segment-only fallback. Relocatable objects, overlapping ordinary allocated/load ranges and sectionless ELFs currently return clear unsupported errors. HEX/BIN analysis and standalone MAP symbol/section analysis are not supported. Dynamic-symbol-only attribution is not yet implemented.
3. **Comparisons:** normalize source roots across build machines, improve duplicate/renamed symbol matching and introduce simple CI budgets. Matching currently uses file label, section and mangled symbol name, with duplicate identities aggregated. Differences in attribution or debug availability can affect per-file/symbol deltas.
4. **Stack:** import evidenced call graphs and represent recursion, indirect calls, assembly, interrupts and missing data before estimating call chains. The model reserves these uncertainty categories. CFA/disassembly, RTOS task stacks and runtime high-water marks are later inputs.
5. **Desktop delivery:** validate on representative user firmware and Linux desktops, refine large-report performance, add installers, accessibility/keyboard review and preferences. Source tables currently rebuild their display rows each frame, although visible rows are virtualized. Region occupancy and largest-contributor rankings are cached per analysis. Workspace preferences remember the folder, firmware, layout, view and overview memory selection. Refresh (F5) rescans and reloads the selected firmware while preserving the last successful report on failure. Preferences are stored in `snout-firmware-explorer/workspace.json` under the user configuration directory (APPDATA on Windows, XDG_CONFIG_HOME or ~/.config elsewhere). Use **Settings > Open configuration folder** to open Snout’s settings and snapshot directory in your system file explorer. No export dialog is included yet; use CLI JSON for export.

No VS Code dependency is present. A future extension or CI service can consume core reports or the CLI without the desktop frontend.

### Thread-local storage

Generic TLS analysis uses standard ELF `PT_TLS`, `SHF_TLS`, and `STT_TLS` metadata. Reports show the initialized and zero-initialized template sizes, alignment, and TLS variables with template offsets. When `PT_TLS` is absent, the template extent is inferred from allocated TLS sections, including internal gaps. Initialized section payload remains in Flash accounting; TLS templates are excluded from static RAM and physical runtime ranges. ELF template addresses may overlap ordinary runtime sections.

The template size is a per-thread requirement, not a complete allocation size. Total TLS RAM remains unknown: the ELF does not establish live thread count, ABI/runtime overhead, or whether TLS occupies already-counted stack reservations. No RTOS-specific assumptions are applied. TLS variables are listed separately; DWARF source attribution for TLS remains unsupported.
